# Firebase concept room client handoff

This branch replaces the **browser** Supabase adapter and `/admin/` with Firebase Web SDK. It does not deploy, create rules, import records, or configure a project. The old Supabase SQL and Node CLI are historical artifacts; `tools/concept-admin.mjs` is **not** a Firebase importer and must not be used against this branch.

## Build

Set the five public `PUBLIC_FIREBASE_*` variables in `.env.example` to the Firebase Web app values before building. Never put service-account credentials in these variables. Run `npm ci`, `npm run build` (includes Astro check and tests), and host `dist/` at the configured Astro base path. With no config, the UI explicitly reports the missing connection; it does not display demo records. Anonymous Authentication must be enabled. The browser must be allowed to read Storage objects through Firebase SDK `getBlob` (check CORS on the Storage bucket for the hosting origin).

## Data contract / rules the infrastructure owner must implement

- `concepts/{sourceUUID}` contains the source snake_case concept fields plus `reviews: [source review rows]` and `concept_assessments: source assessment row | null`. Historical IDs and timestamp strings are retained. Catalogue reads query `where(locale == requested)` plus `where(publication_status == 'published')` for non-editors; editors query locale alone and see drafts. If Firestore requests an index, create it for the locale + publication_status pair. Each catalogue request needs exactly one concepts query; media is fetched separately only when visible/opened.
- `reviews/{id}` is create-only, never update/delete. On a review, one Firestore transaction sets the archive row and updates the concept's embedded `reviews` array. An editor decision/reset also changes `publication_status` in that transaction. New row keys: `id, concept_id, reviewer_id, reviewer_role, decision, notes, affects_decision, clear_prior_notes, supersedes_review_id, created_at`. `reviewer_id` is the current Firebase Auth uid; imported historical rows keep their source UUIDs. `wait` is legacy display-only, not a new decision.
- `concept_assessments/{conceptId}` and the embedded object update in one transaction, with `concept_id, production_speed, budget_level, updated_at, updated_by` (plus retained source fields). Category updates to the concept in the same transaction. Both assessment and editorial metadata writes require `profiles/{uid}.identity_kind == 'content_editor'`.
- `profiles/{firebaseUid}` is the active self-owned profile. The client explicitly selects a role and writes `display_name, identity_kind, is_editor, approved, created_at, updated_at`; `content_editor` is **open to every link holder**, as requested (no email allowlist). `legacy_profiles/{sourceUUID}` is a read-only archive; do not use those UUIDs for new authorship.
- `concept-banners/{sourcePath}` and `concept-pdfs/{sourcePath}` are private Storage keys. Rules should allow authenticated readers only for referenced published assets (editors may access drafts), and writes only for self-selected editors. The client never calls `getDownloadURL`. It calls authenticated `getBlob`, creates transient object URLs, and revokes them on reader close, language switch, admin preview change, and pagehide. New file versions get new UUID folders and the old objects remain. Banner restoration is an optimistic-concurrency pointer update.
- `/admin/` offers draft creation, existing concept text/locale/category/order/status/media editing, a manifest-backed bulk import, draft publishing, and versioned banner composition/title correction/restore. A newly created concept is written only after its uploaded objects are ready; an edit uses an optimistic transaction. Source history/assessment remain unchanged by metadata edits.

**Security note:** Since every link-holder can elect `content_editor`, this is an intentionally open editorial policy, not an invitation-based privilege boundary. Rules must validate payload ownership and consistency even under that policy. Do not expose private Storage objects through permanent token URLs. Firebase Web SDK reads require client-side environment values at *build time*; no live Firebase integration was exercised in this branch before project configuration/import/rules.
